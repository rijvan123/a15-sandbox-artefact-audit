# Code amendment before the freeze, 3 November 2026

## What happened
- `ingest --inst I1` (MELD-DS-448) stopped twice in folder 54 of the 61 solid blocks of `cape_reports.7z`:
  run 1 on 2 Nov after 23,278 of 26,166 reports (last seal 11:54:52 UTC), run 2 on 3 Nov after 23,270
  (last seal 08:12:58 UTC). Neither wrote `outputs/ingest_I1.json` or an anchor, and the logs are empty,
  so the process was ended from outside without a Python error (most likely the Linux out-of-memory killer;
  confirm with `sudo dmesg`).
- `ingest --inst I2` (WinMET, five archives, 31,844 reports) completed on 2 Nov at 22:50:12 UTC (anchor entry 55150).
- Ledger check on 3 Nov 07:24 UTC: 71,696 entries, chain intact, all three anchored Merkle roots match.
  Entries 28-23305 (run 1) and 55151-78420 (run 2) are the seals of the two stopped I1 runs; they stay in the ledger
  as the record of those attempts, and the anchor at the end of the next I1 run covers entries 55151 onward.

## Change
- `a15/cape.py`, `stream_7z`: py7zr 0.22.0 keeps the decompressor of every finished folder (with its 16 MiB LZMA2
  dictionary) on the Folder object until the archive is closed, so memory grew with every folder of the 61-folder
  I1 archive. Each finished folder's decompressor is now released as soon as the next folder starts.
- `run_s9.py`, `ingest`: prints a progress line with current and peak memory every 500 reports, and records
  `peak_rss_mb` in `outputs/ingest_*.json`. Nothing else changes; the records written are identical.

## Verification
- Unit tests: 24 of 24 pass.
- Self-test on MALVADA's 200 reports: records file byte-identical to the earlier run; self-test lexicon digest
  unchanged (f72baaff0a447bd4978f7e2b6ea4e8a3109035e3ae06620aaa39c0c852592eaa).
- Real I1 archive (folders 0-2 on the Cowork VM): one live decompressor at every folder change; memory did not grow.
- New SHA-256: a15/cape.py 904383f6752f01811c48795ad92b21ecf0a23ec9dff2abf17f17fcdd85ae98c5;
  run_s9.py 130df1936eb059996efeb5efa04b91c2b18258d478b0af3e093b08161b319c73 (all digests in ../SHA256SUMS_s10_engine.txt).

## Cause confirmed (authors' WSL `dmesg`, 3 November 2026)
- Both runs were ended by the Linux out-of-memory killer: `Killed process 11174 (python) ... anon-rss:7486888kB` and
  `Killed process 15359 (python) ... anon-rss:7415780kB`. WSL had 7 GB of memory and 2 GB of swap.
- Mechanism: py7zr reads 1 MiB of compressed input on every decompress call, but an average MELD report needs only
  about 0.37 MB of input (compression about 27:1), so up to about 100 MB of unconsumed input builds up in each
  folder's lzma decompressor, whose buffer is never shrunk. Because py7zr kept every finished folder's decompressor,
  about 115 MB per folder (buffer plus 16 MiB dictionary) stayed in memory: about 6-7 GB by folder 54, consistent
  with the measured 7.4 GB. WinMET's folders are about 33 MB of packed data each and memory was reset with each of its
  five archives, which is why Step 8 completed.
- With the amendment above, only the current folder's decompressor is alive; the expected peak is about 2 GB
  (estimate, at the 316 MB report), well within the 7 GB available.


# Amendment 2 before the freeze, 3 November 2026: the stages after ingest read the records one at a time

## Why
- `audit`, `harmonise`, `lexicon`, `overlap` and `dryrun` loaded every sealed record of both installations into
  memory at once. On a 2,500-record test fixture (18.6 MB of gzip records) they peaked at 2.3-4.1 GB and the dry run
  was stopped by the out-of-memory killer at 8 GB (measured). The real records are 1.05 GB of gzip records
  (I1 235 MB, I2 816 MB), so these stages could not run on the 7 GB WSL machine.

## Change
- `run_s9.py`: `iter_records` reads the records one line at a time, in the order the earlier `_records` returned them.
  Each stage keeps only what it uses:
  - `audit`: every field except the call list (then the unchanged `field_audit`).
  - `harmonise`: per trace, the SHA-256, labels, time keys and the set of API names; for WinMET also the API 3-gram set
    and its MinHash signature. The label of the first retained WinMET trace of a binary comes from a dictionary instead
    of a search over all traces (same value).
  - `lexicon`: the set of token types (the lexicon file depends only on this set).
  - `overlap`: per-trace token counts (`overlap.CountBuilder`), then `overlap.class_overlap_counts`, the earlier
    `class_overlap` split in two. Counts are whole numbers and every sum is exact in float64, so the result does not
    depend on how the matrices were assembled.
  - `dryrun`: pass 1 reads identities and labels and makes the selection exactly as before; pass 2 keeps the collapsed
    sequences of the selected traces only, as the whole sequence up to 512 elements or else its first and last 256
    (`tokens.head_tail_store`): enough for head-plus-tail truncation at any L the rule can choose (L <= 512; the
    stage now stops with a message if L < 2).
  - Progress lines every 2,000 records with current and peak memory; `outputs/runinfo_<stage>.json` records time,
    peak memory and, for `harmonise`, the near-duplicate clustering counts. These files are not part of any frozen file.
- `a15/dedup.py`, `test_clusters`: candidate pairs come from `candidate_neighbours`, one trace at a time, instead of
  one Python set of all pairs (about 15 million pairs for WinMET, estimated from a 5% sample, so about 2 GB in that
  set). Each pair is visited once in increasing (i, j) order; a pair already inside one cluster is skipped; the exact
  Jaccard index uses `jaccard_sorted` (binary search, same value as `jaccard`). Same partition and the same
  cross-label count as before. Cluster ids are now numbered by each cluster's first member. Before, they were the
  ranks of whichever roots union-find kept, which depended on the iteration order of a Python set (CPython-specific).
  Consequence: the WinMET grouped split (`split_I2_grouped.json`) places the same clusters, but in a different random
  order, than the earlier code would have; the split no longer depends on the Python version.
- Fix: `stats.half_width` returned a NumPy float, so `gates.k5_p4` returned NumPy booleans. The earlier dry run wrote
  them as the strings "True"/"False" in `dryrun_K5_K6_P1_P4.json` and then stopped with a TypeError when writing the
  gate entry to the ledger. `half_width` now returns a Python float and the gate dictionaries hold Python booleans.

# Amendment 4 before the freeze, 5 November 2026: dry-run training length, K6 timing and thread count

## Why
- The dry run of 4 November trained its model for 3 of the 5 requested epochs. `train_deep` stops when the
  validation score has not improved for `patience` (3) epochs; the dry run passes no validation set, so every score
  was NaN and training always stopped after epoch 3. The model reached a mean within-installation recall of 0.35 and
  predicted 6 of the 9 families. K5 and P4 are computed from this model (K5 projected 3.20 points; P4 ratio 0.68).
- The K6 input timed one configuration (first draw of seed 0: Transformer with 4 layers, the largest in the search
  space; BiLSTM with 2 layers) on 16 traces, best of 2 passes. On 4 November at L = 256 it gave 141 ms (Transformer),
  717 ms (BiLSTM) and 12.0 ms (1D-CNN) per trace: more than on 3 November at L = 512 for the same model (92, 292 and
  4.7 ms), and 9, 22 and 5 times the same measurement on a 2-CPU cloud machine on 5 November (15.4, 33.2 and 2.3 ms;
  measured on sandbox). The projection for the CPU plan was 342 h instead of about 72 h. `a15/models.py` sets PyTorch
  to every logical CPU; small sequence models can run much slower on many threads, because each operation waits for
  the slowest thread, and a busy machine makes this worse. The pattern fits: the BiLSTM (many small operations) lost
  most, the 1D-CNN (few large operations) least.

## Change
- `a15/models.py`: `train_deep` applies early stopping only when a validation set is given, and reports
  `epochs_run`. New `time_per_trace_configs`: mean, minimum, maximum and per-configuration cost of a list of
  configurations. The thread count is read from `A15_THREADS`; unset, it is every logical CPU, as before.
- `run_s9.py`, `dryrun`: `--epochs` defaults to 10 (was 5), the epochs the K6 projection assumes. The K6 input is the
  mean over the 8 search configurations of seed 11 (the first of them is the configuration the dry run trains), each
  the best of 3 passes over 32 traces at L. Recorded beside it in `dryrun_K5_K6_P1_P4.json`: the earlier
  single-configuration value, the measured training time per trace and epoch of the dry-run model, CPU count, thread
  count and load average, `epochs_requested` and `epochs_run`.
- New `bench_threads.py`: times the three learners at thread counts 1, 2, 4, ... up to the number of logical CPUs,
  prints the CPU-plan hours for each and the fastest. It reads no data and writes no file; the thread count changes
  speed, not results.
- `tests/test_harness.py`: 39 tests (3 new): training runs every epoch without a validation set and still stops
  early with one; timing over configurations; the thread check.
